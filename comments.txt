DDL этапов создания слоёв DWH находятся в соответствующих файлах формата .sql: stg_renewal_ddl.sql обновляет stg-слой нашей БД, добавляя туда новые таблицы; dds_renewal_ddl.sql обновляет слой детализированных данных, изменяя имеющиеся таблицы и добавляя новые; cdm_courier_ledger_ddl.sql создаёт таблицу для витрины данных, нужной по заданию проекта.
Для заполнения слоёв DWH (stg, dds, cdm) для проекта (данные о курьерской службе - курьерах и доставках) необходимо в airflow запустить DAG'и:
    1) load_all_to_stg - загрузка данных из источников Postgre и MongoDB (текущие задания в уроках спринта)
    2) stg_delivery_api_load - загрузка данных из API (задание проекта)
    3) load_to_dds_new - загрузка из stg-слоя в dds (был написан для текущих заданий в уроках спринта и дополнен в проекте)
    4) load_courier_ledger - загрузка витрины из dds слоя 

В целях большей безопасности уже работающего кода загрузки DAG'а для загрузки из Postgre и MongoDB ("работает - не трогай!") я решил, что загрузку из API лучше сделать отдельным DAG'ом - так как на данном этапе данные не связаны между собой, порядок загрузки не важен, а значит, нет опасности в случае неправильной последовательности работы этих двух ДАГов.
Напротив, DAG загрузки в DDS очень чувствителен к очерёдности загрузки данных, так как появляются связи и зависимости между таблицами, поэтому я обновил уже существовавший DAG из спринта, дополнив его функциями для новых задач (поэтому у него в названии есть слово "_new").
DAG для загрузки витрины, которую писали в течение спринта, я не указывал в списке необходимых, так как для проекта эта витрина никакого влияния не оказывает.
